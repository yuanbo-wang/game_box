## 二、背景与目标

### 2.1 背景

- 个人开发者以**个人主体**开发微信小游戏，仅能纯 IAA 变现（不可开通内购，见 11.2）。
- 推箱子品类存在结构性缺陷：单局时长偏长、"47 步 vs 43 步"的成绩没有天然可比性。
- v4.0 方案针对以上问题重做：**限步二值化（过/不过）+ 小镇每日赛（全服同题）+ 贴纸级美术**，并以 3×2 周 MVP 验证两条死活线后再投入完整版。
- 平台前置事实（2026-10 核查，详见 docs/05 第 2.5 节）：ICP 备案强制、软著自助办理 0 元、流量主需累计 UV≥1000、纯 IAA 解谜可走免版号通道。

### 2.2 要解决的问题（按优先级）

| 优先级 | 问题 | 对应设计 | 验证阶段 |
|:---|:---|:---|:---|
| P0 | 内容成本（死活线 1）：关卡不能靠手工设计 | 程序生成 + 校验器过滤；每日赛批量预生成 | 第 1-2 段 |
| P0 | 分享必然性（死活线 2）：分享必须是机制的一部分 | 每日赛 + 结果海报 + 魔鬼关卡 | 第 1-2 段 |
| P1 | 失败痛感不足：玩家感受不到"差一点" | 限步通关 + 步数锁死（过/不过二值化） | 第 1 段 |
| P2 | 变现依赖获量：先有量、后有钱 | 加步复活等"玩家主动想看"的广告点 | 第 2 段起 |

### 2.3 成功指标与口径

| 指标 | 定义 / 口径 | 目标 | 测量阶段 |
|:---|:---|:---|:---|
| **自发分享（测试）** | 20 人测试中主动截图分享成绩的人数 | **> 0（核心判据）** | 第 1 段 |
| 单关平均重试次数 | 人均单关重复挑战次数（重开本关计 1 次） | ≥ 2 | 第 1 段 |
| 教学关完成率 | 完成教学关人数 ÷ 进入教学关人数 | ≥ 90% | 第 1 段 |
| 魔鬼关完成率 | 同上口径，分母为进入魔鬼关人数 | 30-70% | 第 1 段 |
| 每日赛参与率 | 当日玩过每日赛人数 ÷ 当日 DAU | 记录基线 | 第 2 段 |
| 分享率 | 分享次数 ÷ DAU | 记录基线 | 第 2 段 |
| 7 日留存 | 第 N 日新增用户在第 N+7 日回访 ÷ 第 N 日新增 | 记录基线 | 第 2 段 |
| 复活广告完播率 | `ad_complete` ÷ `ad_show`（复活场景） | **条件性基线**（以流量主开通为生效条件；未开通期无测试对象） | 第 2 段起（广告实际生效自流量主开通后） |
| ARPDAU（监控） | 人均日观看次数 × eCPM ÷ 1000 | 保守口径 ≈0.06 元 | 持续 |

> 口径说明：标注"记录基线"的指标不设绝对阈值，作为第 3 段决策矩阵（继续/迭代/转向/止损）的判断依据（依据 docs/04 第 3.5、4.1 节）。eCPM 采用 25 元保守口径，非收入承诺。
> **条件性基线说明**：第 2 段体验版种子量为 100-300 人（docs/04 3.5），累计 UV 远达不到流量主开通门槛（UV≥1000），故第 2 段**不接真实激励视频**——"加步复活"走**本地占位/降级路径**验证状态机与出口；"复活广告完播率"在第 2 段**无测试对象**，顺延至流量主开通后（详见 FR-04、FR-15、13.2）。

## 三、名词与术语定义

| 术语 | 含义 |
|:---|:---|
| 小物件 | 可推动的目标物（南瓜、毛线球、礼物盒、小蛋糕） |
| 星光台 | 物件的目标放置点 |
| 机关 | 可交互机制：传送带 / 滑梯弹簧 / 小伙伴 |
| **限步通关** | 每关有步数预算，耗尽未完成即失败（结果二值化：过 / 不过） |
| **步数预算（maxSteps）** | 关卡允许的最大步数 = 最优步数 + 容错余量 |
| **步数锁死** | 撤销回退棋盘，但**不返还**已消耗的步数 |
| **容错余量** | maxSteps − optimalSteps；教学 +8~10 / 普通 +4~6 / 魔鬼 +1~2 |
| 最优步数（optimalSteps） | 关卡最少通关步数，由求解器算出（派生 maxSteps 的基数） |
| 魔鬼关卡 | 每章第 8 关，容错余量最小的刻意卡点 |
| **小镇每日赛** | 全服每天同一关、每人一次机会、比步数 |
| 一次机会 | 每日赛每人每天 1 次挑战机会，不支持重开 |
| 加步复活 | 步数耗尽后看激励视频 +3 步（主线每关 1 次 / 每日赛每日 1 次） |
| 击败百分比 | 每日赛成绩优于我的玩家数 ÷ 当日提交总人数 |
| 结果海报 | 每日赛成绩分享图（步数 + 击败百分比 + 小程序码位） |
| 加油 | 最轻量求助形态：好友点一下，双方各得奖励 |
| 断供降级 | 每日赛关卡拉取失败时，降级为"昨日关卡重玩" |
| 预生成管线 | 批量生成每日赛关卡并强制校验的离线工具（幂等） |

## 四、需求范围

### 4.1 包含（按阶段）

| 阶段 | 周期 | 包含需求 | 出口标准 |
|:---|:---|:---|:---|
| **第 1 段（MVP-1）** | W1-2 | 限步引擎（移动/推动/撤销锁死/结算）、传送带、10 关（3 教学 + 4 传送带 + 2 综合 + 1 魔鬼）、本地成绩、对比卡片、**加步复活（引擎部分 `revive()`）**、**免费提示（3 次/关）** | Go/No-Go 1（自发分享 > 0；重试 ≥2） |
| **第 2 段（MVP-2）** | W3-4 | 每日赛（云函数）、一次机会状态机、加步复活（激励视频**代码就绪；实际生效以流量主开通为前提，未开通期走降级路径**）、击败百分比、结果海报、四条基线埋点 | Go/No-Go 2（基线数据支持继续） |
| **v1.0 完整版** | W7-14 | 30 关、滑梯弹簧、小伙伴、求助-加油、6 个广告场景全量、全量埋点、隐私/适龄/防沉迷合规组件 | 提审上线 |
| **v1.1 扩展** | 上线后 | 1v1 挑战链接、好友榜（开放数据域）、角色换装、音乐花丛、镜子小屋 | 按上线数据评估 |

### 4.2 不包含（明确不做）

| 事项 | 原因 |
|:---|:---|
| 内购 / 虚拟支付 | 个人主体不可开通（见 11.2） |
| Banner / 插屏广告 | 破坏解谜沉浸感 |
| 总榜、具体排名展示 | 弱者被碾压，与治愈系定位冲突（只给"击败 X%"） |
| 买量投放 | 单位经济不支持（7 日 LTV ≈0.44 元，见 docs/05 2.3） |
| 社交聊天 / UGC / 用户间交易 | 非核心链路，且带内容审核成本 |
| "分享才能复活 / 才能继续"类设计 | 平台不鼓励、伤体验（反骚扰硬约束） |
| 音乐花丛、镜子小屋 | v1.1 评估（静音不可玩 / 成本过高） |

### 4.3 需求优先级与排序依据（2026-10-10 补充）

**排序方法**：项目处于验证期，Reach 类指标无实测值，**不采用纯 RICE 打分**（避免伪精确）；MVP 核心链路是强依赖序列，按「依赖 + 战略」排序——先"验证装置"、后"体验扩展"。简化 RICE 仅用于完整版候选项（见 4.3.2），数值均标注为估算。Kano 定性参考：引擎与结算=必备型、每日赛与海报=兴奋型、装扮类（v1.1）=期望型。

## 五、方案对比与选型说明

### 5.1 推进节奏（采用方案 A）

| 维度 | 方案 A：3×2 周三段验证 **【采用】** | 方案 B：13 周直投完整版 | 方案 C：纯单机版 |
|:---|:---|:---|:---|
| 实现成本 | 低（6 周见结论） | 高 | 最低 |
| 风险 | 最低：最大不确定性前置暴露 | 最高：未验证假设同时下注 | 中：无法验证分享必然性 |
| 结论 | **采用** | 否决（赌注太大） | 否决（丢掉死活线 2 的验证装置） |

### 5.2 第三层社交形态（采用每日赛）

| 维度 | 1v1 挑战链接 | **小镇每日赛【采用】** |
|:---|:---|:---|
| 内容成本 | 每次挑战一套链路 | 每天 1 关，批量预生成 |
| 分享必然性 | 需玩家主动发起 | 全服同题 + 海报，讨论由机制产生 |
| 公平性 | 链路传递存在刷分风险 | 每人一次机会 + 服务端强校验 |

1v1 挑战链接不删除，降为 v1.1 扩展（见 4.1）。

### 5.3 演进路径（本期 → 后续 + 触发条件）

| 迁移 | 触发条件 | 动作 |
|:---|:---|:---|
| MVP → 完整版 | 第 3 段结论"继续"（分享率与参与率健康） | 扩 30 关 + 补 2 机制 + 变现 + 提审 |

| 任意阶段 → 转向 | 两条死活线两轮验证均不成立 | 复用引擎换题材（约 4 周，见 docs/04 第 4 节） |

## 六、用户角色与使用场景

### 6.1 角色

| 角色 | 特征 | 核心诉求 | 对应设计 |
|:---|:---|:---|:---|
| 核心玩家 | 18-35 岁治愈系轻度玩家，碎片时间 | 2 分钟内一关、低挫败、可爱 | 教学关余量充足、撤销救棋局、贴纸级美术 |
| 传播玩家 | 爱晒成绩、爱比一比 | 有东西可晒、有由头可比 | 每日赛结果海报、"击败 X%" |
| 回流玩家 | 被朋友圈/群海报吸引而来 | 3 秒上手、今天就能参与 | 免注册即玩、每日赛直达入口 |
| 好友（被求助者） | 收到求助卡片的微信好友 | 点一下不麻烦、有回馈 | 加油即可、双方得星星 |

### 6.2 用户故事（含验收标准）

**US-01 玩一关（核心玩家）**
作为核心玩家，我想要在碎片时间里快速玩一关，以便获得轻松的成就感。
- Given 首次进入且未玩过教学关，When 开始第 1 关，Then 有图文教学提示，且容错余量充足（+8~10）几乎必过。

**US-02 撤销救棋局（核心玩家）**
作为走错一步的玩家，我想要回退棋盘，以便重新尝试（即使步数收不回来）。
- Given 已消耗 5 步且把物件推到死角，When 连续撤销，Then 棋盘逐步回退且剩余步数不变，UI 明示"步数不返还"。

**US-03 "就差一步"（传播玩家）**
作为被魔鬼关卡卡住的玩家，我想要表达"我差一点就过了"，以便在群里晒/哭惨。
- Given 在魔鬼关卡步数耗尽，When 结算，Then 显示不羞辱的失败文案与"再试一次/分享"入口。

**US-04 每日赛与海报（传播玩家）**
作为每日来玩一次的玩家，我想要知道我今天水平如何，以便发个海报证明实力。
- Given 今日未挑战，When 完成每日赛并提交，Then 显示"用了 X 步 · 击败 Y% 的镇民"并可生成海报。

**US-05 看海报回流（回流玩家）**
作为收到海报的好友，我想要立刻玩"今天这关"，以便跟朋友比一比。

**US-06 求助-加油（好友）**
作为被求助的好友，我想要轻松帮上忙，以便朋友开心、我也顺手有奖励。
- Given 收到求助卡片，When 点击加油，Then 玩家得 1 次提示、好友得 1 颗星星，且 24 小时内不重复打扰。

**US-07 加步复活（失败玩家）**
作为"差 3 步就过"的玩家，我想要马上再试一次，以便今天就过掉这关。
- Given 主线失败且未用过复活，When 完整看完激励视频，Then 步数预算 +3、棋盘保留、继续挑战。

### 6.3 场景地图（主流程 / 分支 / 异常）

- **主流程**：进入 → 教学关 → 主线推进 → 卡关（魔鬼关/普通关）→ 求助或复活 → 每日赛 → 海报分享

## 七、功能需求

> 标记说明：【MVP-1】第 1 段交付 ｜【MVP-2】第 2 段交付 ｜【v1.0】完整版交付 ｜【上线前】合规类
> 验收标准统一采用 Given / When / Then 格式；"必须/应该/可以/禁止"为规范用词。

### 模块 A：基础操作与限步

**FR-01 移动与推动**【MVP-1】
- 描述：滑动屏幕（或方向键）使角色移动一格；目标格有物件时尝试推动（只能推、不能拉）。
- 规则：
  - 有效移动（纯移动或推动）消耗 1 步；非法操作（撞墙/越界/推不动）**禁止**消耗步数
  - 一步只能推一个物件
  - 长按角色高亮当前可推动物件范围（辅助）
- 验收：
  - G1：Given 角色右侧为墙，When 向右滑动，Then 角色不动、步数不变、给出轻反馈
  - G2：Given 角色右侧为物件且物件后是平地，When 向右滑动，Then 物件与角色各右移一格、步数 +1

**FR-02 撤销与重置（步数锁死）**【MVP-1】
- 描述：撤销用于"救棋局"，不用于"省步数"。
- 规则：
  - 撤销无限次；回退棋盘一步；**步数锁死：不返还已消耗步数**（v4.0 核心规则）
  - 撤销按钮旁**必须**常显"步数不返还"说明；首次触发撤销时**应该**强提示一次
  - 重置（重开本关）：重置棋盘与步数预算；主线允许无限重试（内容体验优先）；**重开后复活次数归零、`stepBudget` 恢复初始 `maxSteps`（丢弃已加的 +3）**；每日赛不支持重开（见 FR-10）
  - 胜利/失败态下撤销被拒绝
- 验收：
  - G1：Given 已走 3 步，When 点撤销，Then 棋盘回退一步、剩余步数仍为原预算 −3
  - G2：Given 连续撤销至初始棋盘，Then 已消耗步数不回升（保持 3）

**FR-03 步数预算、失败判定与结算顺序**【MVP-1】
- 描述：每关步数预算由管线派生，耗尽未完成即失败。
- 规则：
  - `maxSteps = optimalSteps + 容错余量`（教学 +8~10 / 普通 +4~6 / 魔鬼 +1~2），**禁止**人工拍脑袋估算
  - 剩余步数常驻且最醒目；剩余 ≤2 时进入**告急态**，采用**三种独立信号**（多通道、不依赖单一颜色）：① 剩余步数变红 ② 步数图标形状/边框变化 ③ 数值闪烁（可叠加心跳音效）；**静音或色弱场景下仍需可辨识**
  - 结算顺序**必须**固定：胜利 → 步数耗尽失败 → 死局提示；**死局检测为启发式**（有限深度 BFS：深度上限 10、有状态数上限保护），**不承诺 100% 准确**，仅作**软提示**（文案"可能走不通，试试撤销"），**不改变状态机、不阻断移动/撤销/重开、不触发失败**
  - **最后一步完成归位必须判胜利**，不得判失败（边界）
  - 失败后棋盘冻结；出口：加步复活（每关 1 次）/ 重开本关 / 求助
- 验收：
  - G1：Given 剩余 1 步且该步完成全部归位，When 移动结算，Then 判胜利（不得出现失败态）
  - G2：Given 步数耗尽未完成，When 进入失败态，Then 展示复活入口，且此后移动被拒绝
  - G3：Given 剩余步数 = 2（触发告急态），When 结算，Then **三种独立信号必须同时出现**（① 步数变红 ② 图标形状/边框变化 ③ 数值闪烁）；**关闭音效后三种视觉信号仍需全部存在**（不依赖声音）
  - G4：Given 局面被启发式判定为"疑似死局"，When 提示出现，Then 仅展示软提示，玩家仍可撤销/重开，且**不进入失败态**

**FR-04 加步复活**【引擎 MVP-1 / 每日赛广告 MVP-2 / 主线广告 v1.0】
- 描述：步数耗尽后看激励视频 +3 步，继续当前棋盘。
- 规则：
  - 复活效果：解除失败态、stepBudget +3、棋盘不动（引擎能力第 1 段即有，广告接入后置）
  - **主线**：每关 1 次，计数按"**本关本次挑战**"（重开后归零，`stepBudget` 同时恢复初始 `maxSteps`）；主线为单机，计数存本地，清缓存可重置属**可接受**（不涉奖励发放）
  - **每日赛**：每日 1 次，**服务端计数**——以 `DailyAttempt.usedRevive` 标记为准（`DailyAttempt` 契约见 FR-10 / 10.1）；该标记由服务端在发放加步前写入，客户端**入参禁止**携带或用 `usedRevive` 决定预算（见 11.3）
  - 只在失败态且未用完次数时展示入口；非失败态**禁止**展示
- 验收：
  - G1：Given 主线失败且未用过复活，When 广告完整播放结束，Then 预算 +3 且可继续移动
  - G2：Given 每日赛已用过 1 次复活，When 再次失败，Then 不再展示复活入口
  - G3：Given 主线本关已复活过 1 次，When 重开本关，Then 复活计数归零、`stepBudget` 恢复初始 `maxSteps`
  - G4：Given 每日赛客户端伪造 `usedRevive=true` 但服务端 `DailyAttempt` 无复活记录，When 提交成绩含 +3 步预算，Then 服务端拒绝（INVALID_STEPS）

### 模块 B：机关

**FR-05 彩虹传送带**【MVP-1】
- 规则：物件被推上传送带 → 自动沿 path 运送至末端，朝出口方向再推进一格（若可推进）；**仅"本步刚被推动的物件"触发**（静止不触发）；连锁**最多触发 5 轮**（第 6 轮不再传递，物件停在当前位置、**不报错**）；出口被占用/阻挡时停在传送带末端。
- 验收：
  - G1：Given 物件被推上传送带且出口通畅，When 本步结算，Then 物件出现在出口方向下一格
  - G2：Given 出口为墙，Then 物件停在传送带末端（不越界、不报错）
  - G3：Given 构造 5 层链式传送带，When 推入首端，Then 物件走完 5 轮后停下；构造 6 层时第 6 轮不传递、物件停在第 5 层末端且无异常

**FR-06 滑梯与弹簧**【v1.0】
- 规则：滑梯上物件被推动后沿方向逐格滑行，撞墙/撞物件/达 stopAt 停下；弹簧格把物件弹射 power 格；两者都可能触发机关链（**同样最多触发 5 轮，第 6 轮不再传递、物件停在当前位置、不报错**）；物件**停在**滑梯/弹簧上不触发，被推动才触发。
- 验收：
  - G1：Given 物件被推上滑梯且路径两侧有墙，When 结算，Then 物件停在滑梯尽头前一格
  - G2：Given 弹射路径中途被另一物件阻挡，Then 停在阻挡物前

**FR-07 小伙伴切换**【v1.0】
- 规则：可切换操控主角/小伙伴；**切换不消耗步数**（否则玩家会为省步数不切换）；小伙伴可通过狭窄通道、主角不可；UI 必须高亮当前操控角色。
- 验收：
  - G1：Given 当前操控主角，When 切换至小伙伴，Then 高亮切换、步数不变、可穿过狭窄通道

### 模块 C：关卡与进度

**FR-08 关卡进度与本地成绩**【MVP-1】
- 规则：主线按序解锁；每关记录通关标记与**历史最少步数**（本地）；通关展示"用了 X 步 / 上限 Y 步"对比卡片（截图即分享素材）；进度存本地（换机不云同步）。
- 验收：
  - G1：Given 通关第 5 关用了 12 步（最优 10），When 返回选关地图，Then 显示已通关且在再次通关 11 步后刷新为 11

**FR-09 魔鬼关卡**【MVP-1】
- 规则：每章第 8 关；容错余量 +1~2；设计原则为"看似能过"（前 70% 顺利、最后 1-2 个物件卡死）；失败文案不羞辱（"再想想，你一定可以"）；**必须**保留官方可解的证明路径（防"无解"口碑危机）；失败页提供分享入口（"据说 90% 的人在这里放弃"）。
- 验收：
  - G1：Given 玩家在魔鬼关第 3-5 次失败，When 结算，Then 展示鼓励文案与分享入口，且不展示任何羞辱性表述

### 模块 D：每日赛与传播

**FR-10 小镇每日赛**【MVP-2】
- 描述：全服每天同一关、每人一次机会、比步数。
- 规则：
  - 每天 00:00 全服发布同一关（预生成管线强制校验 `optimalSteps ∈ [6,15]`）；**每日赛步数预算派生规则显式化**：`maxSteps = optimalSteps + 每日赛余量（+4~6）`，由管线派生并写入 `config.meta.maxSteps`，服务端据此计算步数上界（每日赛不套用教学/普通/魔鬼三档，单列"每日赛档"；**余量档 +4~6 经 2026-10-10 用户确认维持**）。拉取失败降级"昨日关卡重玩"（断供保护），**降级源 = 客户端持久化的最近一次成功 `DailyChallenge`（含完整 `LevelConfig`）**，见 10.1
  - **机会消耗时点（统一口径）**：**进入挑战（开始）即消耗当日机会**；服务端在开始时刻写入 `DailyAttempt`（`date` + `openId`，唯一）——与 docs/02 图 4「开始（消耗今日机会）」一致。`getDailyChallenge` 依据 `DailyAttempt` 判定状态：无记录 = 未挑战 / 有记录未提交 = 挑战中（当日可续玩）/ 已提交 = 已提交
  - 每人每日 1 次挑战机会；**不支持重开**（服务端以 `DailyAttempt` 唯一约束强制，堵死"打几步→退出→重进"的变相重开）；步数耗尽 → 加步复活（每日 1 次，**服务端计数**，见 FR-04）→ 继续同一棋盘；仍失败 → 今日无成绩
  - 中途退出保留本地快照，当日可续玩（**续玩属同一 `DailyAttempt`，不消耗新机会**）
  - **跨零点边界**：关卡与成绩绑定"开始时的服务端日期"（`DailyAttempt.date`）；跨零点提交仍计入开始日成绩（不再因 00:00 后日期变化被拒）；未被开始（无 attempt）的当日 24:00 后自动作废；本地快照清理以**服务端日期**为准（次日进入时比对清理）
  - **成绩提交时效界**：仅允许在开始日（`attempt.date`）**当日或跨零点次日**提交；更早的未提交 attempt 提交返回 `EXPIRED`（无成绩，防延迟补交刷旧日榜，见 11.3 / docs/03 §8.3）
  - 记分口径：**当次挑战消耗的步数**（越少越好）；步数并列比用时（duration 口径见 FR-11）
  - 服务端校验通过才计入成绩；客户端**禁止**直接写入成绩
  - 分享不加额外奖励（动机来自结果本身）；**每日主动分享（行为）≤3 次**（对齐 docs/01 6.6；"分享提示弹窗次数"另计，不额外生效）
- 验收：
  - G1：Given 今日未挑战且无 `DailyAttempt`，When 进入每日赛场景，Then 显示"今日尚未挑战"并可开始（唯一 1 次机会）
  - G2：Given 已完成并提交，When 再次进入，Then 显示成绩与击败百分比，不可再次挑战
  - G3：Given 已开始挑战（有 `DailyAttempt`）并中途退出，When 当日再次进入，Then 进入续玩（同一 attempt），**不计为第二次机会、也不允许重开**
  - G4：Given 每日赛关卡拉取失败，When 重试 1 次仍失败，Then 降级"昨日关卡重玩"且关卡可正常游玩（降级源来自本地缓存）
  - G5：Given 23:59 开始、00:01 提交，When 服务端校验，Then 按开始日（`DailyAttempt.date`）计入成绩，不判 `INVALID_DATE`
  - G6：Given 当日 24:00 前未开始挑战，When 次日进入，Then 昨日快照按服务端日期被清理、无残留
  - G7：Given 开始日早于前一日，When 提交成绩，Then 返回 `EXPIRED` 且不生成成绩

**FR-11 每日赛结果与"击败 X%"**【MVP-2】
- 规则：
  - `击败百分比 = 成绩优于我的玩家数 ÷ 今日提交总人数 × 100`（四舍五入）
  - **提交时快照**：成绩提交成功时，**同时快照 `beatPercent` 与 `total`（当日提交总人数）并落库**（`DailyResult.beatPercent` / `DailyResult.total`），此后固定不变，避免"再看就变了"的观感问题；已提交用户再次进入时，`getDailyChallenge` 返回 `{mySteps, beatPercent, total}`
  - **展示时序（统一写死，解决"首次降级 / 复看百分比"打架）**：一律以**提交时快照的 `total`** 判定，且判定结果在本次成绩的**整个生命周期内固定、不回切**：
    - 快照 `total < 20` → **始终**展示降级文案"今日已有 N 位镇民完成"（N = 快照 `total`），**复看时不变**（不因后续人数增长而改为百分比）
    - 快照 `total ≥ 20` → **始终**展示快照 `beatPercent`
    > 即：是否降级只看"提交那一刻"的人数，两种展示不可互切。
  - **禁止**展示具体排名与他人步数
- **用时（duration）口径**：从**首次进入本次挑战（创建 `DailyAttempt`）到成功提交**，跨会话续玩累计，**排除应用后台挂起时长**；duration 为客户端上报、仅用于**步数并列时的排名展示**；服务端另做下界一致性校验（`duration ≥ steps × 理论最短单步操作时长`，**该阈值默认 0.3s/步，由服务端配置下发**，见 11.3），不参与绝对胜负校验（残余风险见 11.3）
- 验收：
  - G1：Given 提交并校验通过，When 返回结果，Then 展示"用了 X 步 · 击败 Y% 的镇民"
  - G2：Given 已提交用户再次进入，When 查询状态，Then 返回与其提交时**相同**的 `beatPercent`（不随当日新增提交变动）
  - G3：Given 提交时快照 `total = 19 / 20 / 21`，Then 分别展示降级文案"今日已有 19 位镇民完成" / 击败百分比 / 击败百分比（阈值 20）
  - G4：Given 步数并列，When 排序，Then 按 duration 升序；伪造超短 duration（< steps × 0.3s）被服务端标记
  - G5：Given 提交时快照 `total = 19`（<20），When 当日人数增长至 30 后再次进入查看成绩，Then **仍**展示降级文案"今日已有 19 位镇民完成"（不回切百分比）；Given 提交时快照 `total = 20`，When 任意时刻复看，Then 始终展示快照 `beatPercent`

**FR-12 结果海报**【MVP-2】
- 规则：海报元素 = 主角形象 + "用了 X 步 · 击败 Y%" + 日期 + 小程序码位；支持保存相册（权限使用时申请）与转发（走官方分享接口）；生成失败可重试，不阻塞结算流程。
- 验收：
  - G1：Given 每日赛完成，When 点击"生成海报"，Then 得到含上述元素的图片并可保存/转发

**FR-13 求助-加油**【v1.0】
- 规则：
  - 发起：卡关超 5 分钟提示求助入口；每人每日 ≤3 次；同一好友 24 小时 ≤1 次
  - 好友：点一下"加油"即完成（无需玩），玩家得 1 次提示、好友得 1 颗星星
  - **禁止**"分享才能复活/继续"；计数服务端校验，不信任客户端
- 验收：
  - G1：Given 今日已求助 3 次，When 再次发起，Then 入口置灰并提示"明天再来找小伙伴吧"
  - G2：Given 好友 24 小时内已帮过我，When 再次发起对该好友的求助，Then 被拒绝并提示

### 模块 E：广告与变现

**FR-14 提示系统**【MVP-1 免费 3 次 / v1.0 广告加购】
- 规则：每关 3 次免费提示；超出后每关最多 2 次"看广告换提示"；提示 = 推荐下一步（引擎 getHint）；提示不返还步数、不改变棋盘。
- 验收：
  - G1：Given 免费提示已用完，When 点"提示"，Then 展示看广告入口；广告完整结束才发放第 4 次提示

**FR-15 激励视频广告（通用规范）**【MVP-2 起】
- 规则：
  - **必须**处理三个事件：`onLoad`（广告可用才显示按钮）、`onError`（降级路径：v1.0 起为「分享求助」；MVP-2 期间为「稍后再试」轻提示——不阻塞流程）、`onClose`（**必须**检查 `isEnded`，未看完不发奖励）
  - 奖励发放**必须**幂等：一次性条件 + 频次计数校验，重复回调不重复发放
  - **禁止**任何"不看完广告就无法继续主流程"的设计；所有观看均为玩家主动选择
  - **降级口径以本 PRD 为准**：MVP-2 为「稍后再试」轻提示、v1.0 起为「分享求助」（docs/01 7.3、docs/03 7.3 的"一律分享求助"措辞待同步，见附录 D）
  - **生效前提**：广告组件**代码第 2 段即就绪**，但**实际生效取决于流量主开通（UV≥1000）**；未开通期所有广告点位走降级路径（不阻塞流程），"复活完播率"为条件性基线（见 2.3、13.2）
- 验收：
  - G1：Given 激励视频 `onClose` 返回 `isEnded=false`，When 返回游戏，Then 不发放奖励并轻提示
  - G2：Given 广告加载失败，When 玩家点击复活，Then 按阶段走降级路径（MVP-2「稍后再试」/ v1.0「分享求助」），不卡死

**FR-16 其他广告点位**【v1.0】

- 不设 Banner 与插屏（见 4.2）。
- **计数存储口径**：凡涉及**奖励发放**的点位（每日赛复活、领取每日奖励、结算"翻倍"）计数**必须服务端**（防清缓存/换机重复领取）；纯增益且不影响公平的点位（主线复活、广告换提示）可本地计数，清缓存可重置属可接受（见 FR-04）。
- 验收：G1：Given 已完成每日奖励领取，When 再次点击，Then 提示"今日已领取"且不再拉取广告（清缓存后再次进入仍显示"今日已领取"）

## 九、业务流程与状态流转

> 图示见 `docs/02-flowcharts.md`：图 3（棋盘引擎状态机）、图 4（每日赛状态流转）、图 6（求助防骚扰）、图 8（每日赛时序）。

### 9.1 关卡状态机（主线）

| 状态 | 进入条件 | 允许操作 | 迁移 |
|:---|:---|:---|:---|
| 进行中 | 创建/重开/复活 | 移动、撤销、重置、提示 | 全部归位 → 胜利；steps ≥ budget → 失败 |
| 胜利 | 结算判定（优先） | 查看成绩、分享、下一关 | 关闭/跳转 |
| 失败 | steps ≥ budget 且未完成 | 复活（1 次/关）、重开、求助 | 复活 → 进行中（预算 +3）；重开 → 进行中（重置） |

### 9.2 每日赛状态机

| 状态 | 进入条件 | 允许操作 | 迁移 |
|:---|:---|:---|:---|
| 未挑战 | 当日 00:00 后，服务端无 `DailyAttempt` 记录 | 开始挑战、查看规则 | 点击开始 → 挑战中（**服务端写 `DailyAttempt`，消耗今日机会**） |
| 挑战中 | 已创建 `DailyAttempt`、未提交 | 移动、撤销、复活（1 次/日）、退出（保留快照，当日可续玩） | 通关 → 提交中；失败且不复活 → 未完成 |
| 提交中/待确认 | 已调用 `submitDailyResult`、结果未确认 | 等待确认、断网重试 | 校验通过 → 已提交；超时/失败 → 保留重试（**幂等键 = `date + openId`，重试不消耗第二次机会、返回既有成绩**） |
| 已提交 | 服务端校验通过 | 查看结果、生成海报、分享 | 次日 00:00 → 未挑战（新关） |
| 未完成 | 步数耗尽未复活/确认失败 | 查看提示、明日再来 | 次日 00:00 → 未挑战（新关） |

> 已定口径：**进入（开始）即消耗机会并写 `DailyAttempt`**；同一 attempt 内退出可续玩；**不支持重开**（`DailyAttempt` 唯一约束强制）；放弃后当日不可重来。
> 状态判定权归服务端：客户端仅缓存展示态，进入每日赛一律以 `getDailyChallenge` 返回为准（`attempts` / `DailyResult` 判定）。

### 9.3 求助-加油流程

发起（校验每日 3 次）→ 生成求助卡片 → 好友点"加油"（校验 24h 冷却）→ 双方发奖（玩家 1 次提示 / 好友 1 颗星星）→ 服务端记录。

### 9.4 广告奖励发放流程

点击入口（校验频次与状态）→ `show()` 展示 → `onClose` 检查 `isEnded` → 服务端/本地一次性条件校验 → 发奖 → 埋点上报。任一步失败 → 降级路径（分享求助/提示稍后再试），不阻塞主流程。

## 十、数据与埋点需求

### 10.1 核心实体

| 实体 | 存储 | 关键字段 | 约束 |
|:---|:---|:---|:---|
| 主线进度 | 本地 `wx.storage` | 通关关卡、每关历史最少步数 | 单机数据，换机不同步 |
| DailyChallenge | 云数据库 | date、levelId、config（含 maxSteps）、createdAt | `date` 唯一索引 |
| **每日赛关卡本地缓存** | 本地 | 最近一次成功拉取的 `DailyChallenge`（含完整 `LevelConfig`） | 断供降级源（见 FR-10） |
| **DailyAttempt** | 云数据库 | date、openId、startedAt、usedRevive | **(date, openId) 唯一**（一次机会 + 复活计数的服务端载体） |
| DailyResult | 云数据库 | date、openId、steps、duration、usedRevive、**beatPercent**、**total**、submittedAt | **(date, openId) 唯一** |
| HelpRequest | 云数据库 | fromOpenId、toOpenId、levelId、helped | 用于 3 次/日 + 24h 冷却计数 |
| 每日赛快照 | 本地 | 棋盘快照（续玩用） | 次日按**服务端日期**清理 |

### 10.2 埋点清单

| 事件 | 触发时机 | 关键参数 | 用途 |
|:---|:---|:---|:---|
| app_launch | 启动 | 来源场景值 | 获量分析 |
| level_start | 进入关卡 | levelId | 漏斗 |
| level_complete | 通关 | levelId、steps、remainingSteps、duration | 难度调优 |
| level_failed | 步数耗尽 | levelId、steps | **流失点分析** |
| level_quit | 中途退出 | levelId、steps | 卡点定位 |
| undo_used | 使用撤销 | levelId、steps | 规则感知度 |
| hint_use | 使用提示 | levelId、isFree | 提示系统健康度 |
| ad_show / ad_complete | 广告展示/完播 | placement | **完播率（对比口径）** |
| daily_enter | 进入每日赛 | date | 参与率分子 |
| daily_complete | 每日赛通关 | date、steps、beatPercent | 竞技质量 |
| daily_fail | 每日赛失败 | date、steps | 难度波动监控 |
| poster_generate | 生成海报 | steps | 分享漏斗 |
| share | 分享行为 | scene、channel | **分享率** |
| help_send / help_received | 求助发出/被帮助 | levelId | 社交链路 |

> **用户标识（必填）**：所有埋点事件**必须**携带 `openid`（用于去重与 DAU 分母计算）；`openid` 不裸传客户端——服务端上报由云函数注入，客户端上报经统一封装注入。
> **事件逐条补参**：`level_start` / `level_complete` / `level_failed` / `level_quit` / `undo_used` / `hint_use` / `ad_show` / `ad_complete` / `daily_enter` / `daily_complete` / `daily_fail` / `poster_generate` / `share` / `help_send` / `help_received` 均需带 `openid` + `ts`。

### 10.3 指标口径（计算式）

- 每日赛参与率 = `daily_enter` 去重人数 ÷ 当日 DAU
- 分享率 = `share` 次数 ÷ 当日 DAU
- 复活完播率 = `ad_complete(placement=revive)` ÷ `ad_show(placement=revive)`
- ARPDAU = 人均日观看次数 × eCPM ÷ 1000（eCPM 取结算值）

> **DAU 口径（统一）**：以云函数侧 `app_launch` 事件的 `openid` **去重**为准（不用微信数据助手的 DAU，避免两套口径）。
> **字段映射**：① 每日赛参与率 —— 分子 = `daily_enter` 按 `openid` 去重、分母 = `app_launch` 按 `openid` 去重；② 分享率 —— 分子 = `share` 事件条数（不去重）、分母 = `app_launch` 按 `openid` 去重；③ 7 日留存 —— 按 `openid` 归因新增队列。

### 10.4 最小数据能力（每版本必备）

- MVP-2：**四条基线周报**（每日赛参与率 / 分享率 / 7 日留存 / 复活完播率（条件性））——云数据库查询 + 埋点台账
- v1.0：微信后台留存与来源数据 + 每日赛日报（参与、成绩分布、断供记录）

## 十一、权限与安全要求

### 11.1 用户与数据权限

| 项 | 要求 |
|:---|:---|
| 玩家数据范围 | 仅可读写**本人**数据；他人成绩**永不**返回，仅聚合展示"击败 X%" |
| 云数据库权限 | 客户端不可直写成绩表；仅云函数可写 `DailyResult` / `HelpRequest` |
| 管理后台 | 本期无后台（数据经云开发控制台人工查询） |

### 11.2 平台边界与隐私合规

- 个人主体**禁止**开通虚拟支付（无内购）；**禁止**诱导分享、强制关注
- 隐私保护指引逐项声明；数据最小化（仅 openid + 游戏数据）
- 防沉迷/实名：按微信小游戏平台策略接入
- 命名与素材合规：不含绝对化用语；提到审核时以平台最新规则为准

### 11.3 防作弊（服务端校验链）

`submitDailyResult` 必须按序校验：
1. 时效界与日期：仅接受"开始日（`DailyAttempt.date`）**当日或跨零点次日**"的提交（更早的未提交 attempt → `EXPIRED`，无成绩）；日期一律取 `DailyAttempt.date`（**开始日的服务端日期**，防伪造历史成绩、防延迟补交刷旧日榜）
2. `optimalSteps ≤ steps ≤ maxSteps (+3 若服务端复活记录存在)`（服务端用关卡配置**重算 `optimalSteps`**、读 `config.meta.maxSteps` 派生上界，**不信任客户端**）
3. `(date, openId)` 唯一（一次机会）
4. 复活次数 ≤1/日（以服务端 `DailyAttempt.usedRevive` 为准，**客户端入参 `usedRevive` 一律不采用**）
5. 用时下界一致性（`duration ≥ steps × 理论最短单步操作时长`；**该阈值默认 0.3s/步，由服务端配置下发，可不下发新版本热调**；不通过则标记，见残余风险）

广告奖励侧：`isEnded` + 一次性条件 + 幂等发放；求助侧：3 次/日 + 24h 冷却均服务端计数。

**防作弊目标边界与残余风险（本版本明确声明）**：
- 本版本为 **区间校验 + 一次机会 + 服务端计数** 的防作弊，**不承诺完全防刷**；标题性表述修正为"防作弊基础校验链"，不再使用"竞技公平生命线"式的绝对化承诺。
- **已知残余风险**：a) 改包客户端可直接提交 `steps = optimalSteps` 冒充完美成绩；b) 本地棋盘快照可被编辑为"物件已在星光台"再提交。当前校验链**无法检测**这两类篡改（服务端不重放操作，`steps` 与快照均为客户端权威；因区间校验只约束上下界，冒充完美成绩仍在区间内）。
- **后续版本加固方向**（触发条件：第 2 段数据或上线后出现异常刷分；记入 14.2）：服务端下发关卡 seed、上报关键操作序列/帧摘要、步数-用时一致性启发式强化、异常成绩人工复核。

## 十二、异常处理清单

| # | 场景 | 期望表现 | 处理策略 |
|:---|:---|:---|:---|
| 1 | 撞墙/推不动 | 操作无效 | 拒绝移动、轻反馈、**不扣步数** |
| 2 | 无历史可撤销 | 按钮不可用 | 置灰，无报错 |
| 3 | 最后一步完成归位 | 判胜利 | 结算顺序固化：胜利优先（见 FR-03） |
| 4 | 步数耗尽 | 失败态 | 冻结 + 三出路（复活/重开/求助） |
| 5 | 广告加载失败（含 `onError`，或**开始拉取后 3s 内既无 `onLoad` 也无 `onError` 的静默失败**） | 降级 | 按阶段降级（MVP-2：稍后再试 / v1.0：分享求助入口），不阻塞；**开始拉取后 3s 未 `onLoad` 即视为"广告不可用"**，入口置为降级路径、不展示"看广告"按钮 |
| 6 | 广告中途关闭 | 不发奖励 | `isEnded=false` → 轻提示，可再次尝试 |
| 7 | 广告回调重复 | 幂等 | 一次性条件校验，禁止重复发奖 |
| 8 | 每日赛拉取失败（断网/超时） | 降级 | 重试 1 次 → "昨日关卡重玩"提示（降级源 = 客户端缓存的最近一次成功 `DailyChallenge`，见 10.1） |
| 9 | 成绩提交超时 | 不丢成绩 | 本地保留重试；已提交则查询返回既有结果（幂等） |
| 10 | 重复提交/重复领奖 | 拒绝 | 服务端唯一约束 → 提示"今日已挑战/已领取" |
| 11 | 本地时间被篡改 | 以服务端为准 | 日期判定全部走服务端时间；跨零点提交按**开始日**（`DailyAttempt.date`）计 |
| 12 | 本地存储异常/清缓存 | 可恢复 | 主线进度提示丢失风险；每日赛以云端为准 |
| 13 | 未成年人时段限制 | 平台提示 | 按平台策略展示限制提示 |
| 14 | 资源加载失败 | 可重试 | 重试 + 提示；不进入不可用状态 |
